# services_master 공통 데이터 규격

분석팀(Q1~Q3)과 LLM·앱팀이 같은 서비스 테이블을 쓰기 위한 규격이다. 생성 코드는 `src/preprocess/ssis_master.py`, 사전은 `src/preprocess/keywords.py`, 검증은 `tests/test_step00_preprocess.py`다.
이 문서의 컬럼 목록과 실제 파일의 컬럼이 다르면 테스트가 실패한다.

## 1. 파일

| 항목 | 값 |
|---|---|
| 경로 | `data/processed/services_master.csv` (`python -m src.preprocess.ssis_master`로 생성. 줄 끝은 OS와 관계없이 CRLF로 고정한다: 원문 `*_raw`의 단독 CR 칸을 따옴표로 감싸기 위해서다. 저장소에는 `.gitattributes`(`eol=lf`)에 따라 LF로 정규화되어 저장되며, 단독 CR 칸은 따옴표 안에 있으므로 읽기 결과는 같다) |
| 함께 생성되는 메타 | `data/processed/services_master.meta.json` (생성 시각, 행·열 수, 입력 원자료 해시, 코드 커밋, 생성 코드 파일 해시 `code_sha256`. `code_dirty`는 생성 코드 파일의 커밋되지 않은 수정만 본다) |
| 인코딩·구분자 | UTF-8 with BOM(`utf-8-sig`), 쉼표 |
| 읽기 | `pd.read_csv(path, dtype=str, encoding="utf-8-sig", keep_default_na=False, na_values=[""])` |
| 키 | `servId` (중복 0, 5,288행: 중앙 461 + 지자체 4,827). 155열(v1 128열 + v3 14열 + 외출 v3 4열 + ⑩ v4 7열 + 앱 영역 v3 2열: `app_domain_partial`, `app_domain_v2`). Q1 분석은 앱 영역 v3 이전 153열 기준으로 작성됨 |
| 기준일 | 수집 2026-10-30 |

## 2. 값 표기 규칙

| 표기 | 의미 | 주의 |
|---|---|---|
| `0`, `1`, `2`, `3` | 라벨 값 (문자열) | 숫자로 바꿔 쓸 때 `N`, `NA`를 먼저 걸러낸다 |
| `N` | 근거 문장이 없어 값을 정하지 못함 | **0(없음·무관)과 다르다.** '확인 불가'이지 '없음'이 아니다 |
| `NA` | 해당 없음 (예: 현금지급형의 cost, 연령 범위의 열린 쪽 경계) | |
| 빈칸 | 원천에 값이 없음 / 아직 채우지 않음(정답셋 칸) | |
| `a|b` | 다중 라벨 구분자 (`need_area_q21`, `app_domain`) | 태그 컬럼은 `, ` 구분 |
| `True`/`False` | 불리언 | |

## 3. 라벨 컬럼과 상태

라벨 속성 `<attr>`마다 다음 세 컬럼이 붙는다.

| 컬럼 | 의미 |
|---|---|
| `<attr>_evidence` | 근거 원문 문장. 필드에서 온 값은 `[field] 컬럼=값` 형태 |
| `<attr>_method` | `field`(구조화 필드) / `rule`(키워드 규칙) / `llm` / `human`. 값이 `N`이면 빈칸일 수 있다 |
| `<attr>_review` | 검수 필요 여부 |

라벨 상태는 method와 review의 조합으로 읽는다.

| 상태 | 조건 | 사용 |
|---|---|---|
| 확정 | `method=human` | 분석·추천에 그대로 사용 |
| 필드 기반 | `method=field`, `review=False` | 사용 가능. 필드 자체의 오류 가능성은 남음 |
| 후보 | `method=rule` 또는 `review=True` | 분석에는 민감도 확인과 함께, 추천에는 '확인 필요' 표시와 함께 |
| LLM 후보 | `method=llm` | 사람 검수 표본 일치도를 확인하기 전까지 후보 |
| 미정 | 값 `N` | 값을 추정하지 않는다 |

**LLM·사람 공통 원칙:** 원문에서 근거 문장을 인용할 수 없는 속성은 채우지 않고 `N`으로 둔다. 0(없음·무관)도 근거 문장이 있어야 한다. 기존 `field` 값을 덮어쓰려면 근거 문장과 함께 `human`으로만 덮어쓴다.

### (D) 접근성 (규칙 후보)

| 컬럼 | 값 | 기준 |
|---|---|---|
| `apply_barrier` | 0~3/N | **v2(2026-11-02 개정).** 신청서 제출부터 선정 결정까지 사용자가 하는 일. 0 온라인 완결·명시적 신청 불필요 / 1 전화·우편·이메일·팩스·대리 / 2 방문 / 3 필수 면접·여러 기관 방문. 이메일은 1이다(Notion 정의). 온라인 접수 후 방문 제출처럼 모든 단계를 거쳐야 하는 필수 순차 방문 절차는 2로 올리고 검수한다. '여러 기관' 3은 현재 해당 0건이며 팀 결정 대기. 신청 경로는 가장 쉬운 값을 택하고, 필수 면접은 추가 요건이라 3으로 올린다. 경로 키워드는 같은 문장에 신청·접수·제출이 있고 '불가' 같은 부정이 없을 때만 쓴다. '심사'는 기관 절차라 쓰지 않는다. 신청 정보가 없거나 '직접 지원'만 있으면 N. 추천·직권은 원문에 사용자 방문·관공서 신청이 있으면 경로대로 두고 검수, 없으면 N + 검수. 원문 근거가 없는 명백한 오분류는 `src/preprocess/review_overrides.py`에서 N으로 되돌린다 |
| `apply_barrier_v1` | 0~3/N | 개정 전 값 (면접은 선정기준 문장까지 읽음, 추천·직권 → 1, '심사' 포함) |
| `apply_interview` | 없음/현장/비대면/불명 | 필수 면접의 형태. 불명이면 outing_need의 신청 쪽 외출을 추정하지 않는다 |
| `apply_channel` | 0~2/N | 면접으로 올리기 전의 신청 경로 값 (비대면 면접일 때 외출 환산에 사용) |
| `use_barrier` | 0~3/N | **기존 정의 유지.** 서비스 이용 형태: 0 집에서 이용(현금·바우처·비대면) / 1 근거리 1:1 방문 / 2 기관 출석·소그룹 / 3 집단·면접·출근 |
| `use_outing` | 0~3/N | **새 컬럼.** 서비스 이용에 필요한 외출 조건(청년삶 F7 외출 단계를 차용). 0 집 안(현금·계좌 입금, 찾아오는 서비스·배달) / 1 근처 짧은 외출(지역화폐·바우처 등 이용권) / 2 목적 있는 방문(가끔·단기, 검진·체험·기관 이용) / 3 정기 외출(주 단위 참여·출석, 직업훈련·인턴·일경험). 대화·대면 여부는 쓰지 않는다. 시설입소는 0~3 척도로 잴 수 없어 N. 가정 방문·제공 인력(도우미·요원 등)이 집으로 오는 방문은 0. 온라인과 방문 중 고르는 서비스는 선택 경로의 최솟값 0 + `[선택 경로]` 표시, 선택이 아닌 단순 혼재는 최댓값 + `[혼재·확인 필요]` 표시. 의료비 현금형은 값을 유지하고 검수 표시(`[의료 이용 전제·확인 필요]`). '상담'이라는 단어만으로 2를 주지 않는다 |
| `repeat_burden` | 0~2/N | 0 1회 / 1 몇 회 / 2 정기·장기. 현금형 지급 주기는 N |
| `remote_complete` | 0~2/N | 2 신청·이용 모두 비대면 / 1 한쪽 / 0 둘 다 대면. **집에서 받음 ≠ 본인 외출 없음 ≠ 비대면 완결**이다. 신청 쪽: apply_barrier 0·1은 비대면(대리만 있으면 제외), 2는 아님, 3은 면접이 비대면이고 경로가 0·1일 때만 비대면(현장 면접은 아님, 면접 불명은 N). 이용 쪽: use_barrier 0이고 use_outing 0일 때만 비대면(바우처·지역화폐 1, 가정 방문은 v1 use_barrier 1이라 비대면 아님). 어느 한쪽이 불명이면 N |
| `remote_complete_v1` | 0~2/N | 개정 전 값 |

### (E) 추천 요소 (규칙 후보)

### 외출필요도와 사용자 외출 상태

`use_outing`·`outing_need`는 **서비스 이용에 필요한 외출 조건**이다. 청년삶 F7은 **청년의 실제 외출 양상**을 측정한다. 0~3 단계를 차용했을 뿐 두 척도가 정확히 대응하지 않으므로, 둘을 비교해 추천 순서에 참고할 수는 있어도 '사용자 단계 ≥ 서비스 단계'를 추천 자격 기준으로 쓰지 않는다. 사용자 외출 상태는 사용자 응답 기반이며 AI가 판정하는 회복 단계가 아니다.

- 판정 순서: 서비스명의 목적(생계 → 필수비용 → 보상 → 일시금) → 본문의 생계 명시 → 서비스명의 기관 대상·다른 용도 → 서비스명·지원내용의 기관 대상 → 본문 나열 항목. 보상·예우는 서비스명에서만 본다(본문의 '국가유공자'는 대상 나열인 경우가 많음).
- 자격 조건 문구('생계·의료급여 수급자', '생계급여 또는 의료급여 수급자', '긴급복지(생계지원)를 받는 가구', '기초생활보장', '지원 제외: …')와 형편 문구('생계 곤란')는 가린다. 서비스명에 다른 용도가 있으면 본문의 '생계급여'는 제도 언급으로 보고 쓰지 않는다.
- `app_domain`의 '경제'는 main만 핵심으로 부여하고 candidate는 `app_domain_pending`에 둔다.
- 의료·돌봄 등 서비스 용도 지급은 ⑩에서 뺀다. Q21 10개 문항에 신체 건강·돌봄 문항이 없어 **현재 Q21 분류상 미분류(N)** 로 남는다. 청년에게 필요 없는 서비스라거나 Q1 범위 밖으로 확정한 것이 아니다.
- 서비스명에 일시금·보상(축하금·위문금·장수수당 등)이 있으면 본문의 '생활 안정' 목적 문구보다 서비스명을 따른다(candidate). 생활 안정 목적이 본문에만 있을 때 living.
- 서비스명의 '○○ 사업비'·'운영비'·'운영 보조'·민간단체·재단 지원은 기관 대상(org_target). 공공근로·자격증 취득비는 취업 용도(⑧).
- **근거가 부족한 경계:** 취업 연계 수당(구직활동지원금 등)은 생활비 명시가 없으면 ⑧만 둔다. 축하금·보상금·자산형성은 실태조사 응답자가 말한 '경제적 지원'에 들어가는지 확인할 자료가 없어 candidate로 두고 민감도 분석에서만 포함한다.

## 5-1. 청년 범위와 사용자 적격성의 층 구분 (v3)

| 질문 | 담당 컬럼·코드 | 판정 단위 |
|---|---|---|
| 청년을 위해 설계된 정책인가 | `youth_scope=A` (`youth_scope_basis`) | 서비스 |
| 청년 연령과 겹치는가 | `youth_age`, `age_min`·`age_max`, `youth_scope=B·C` | 서비스 |
| 특정 집단 자격조건이 있는가 | `target_condition` | 서비스 |
| 이 사용자가 조건을 충족하는가 | `src/recommend/eligibility.py` → 적합 / 불일치 / 확인 필요 | 사용자 × 서비스 |
| 판단할 정보가 부족한가 | 서비스 `N`·`U`, 사용자 미확인·모르겠음·응답 원치 않음 → 모두 '확인 필요' | 둘 다 |

**2026-11-05 품질점검(잠정):** 연령 구간만으로 A(`age_band`)가 되던 서비스 중 대상 문장에 일반·신혼부부·무주택세대구성원·고령자가 함께 있으면 B(`age_overlap`)로 둔다. `tag_only`(생애주기 필드에만 청년)는 원문에 청년 근거가 없는 경우가 많아 B로 유지하되 Q1은 `S2_AB_strict`(tag_only 제외)와 함께 보고한다. 특정 집단 대상이면서 연령 언급이 없는 서비스는 U(`no_evidence`)이며 C로 보내지 않는다.

`youth_scope=U`는 '청년이 이용할 수 없음'이 아니다. Q1은 U를 넣은 결과와 뺀 결과를 함께 보고하고(`src/gap_index/q1_supply.py`), 추천은 U 서비스를 제외하지 않고 사용자 정보와 대조한다.
