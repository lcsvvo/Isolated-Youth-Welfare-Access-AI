# 연구·데이터 분석 공통 산출물 작성 표준

이 문서는 연구 분야, 데이터셋, 분석방법과 무관하게 Codex가 STEP notebook, FINAL notebook, 결과표·그림, 단계별 HTML summary를 작성할 때 적용하는 규칙이다. 분석방법을 정하는 문서가 아니라 **실행 근거를 추적하고, 동일한 결과를 재사용하며, 해석의 범위를 정확히 전달하기 위한 산출물 표준**이다.

문서 내 “필수/금지”는 준수해야 하는 규칙, “권장”은 프로젝트 여건에 따라 이유를 남기고 조정할 수 있는 기본값이다. “해당 시” 항목은 적용 여부와 이유를 기록한다. 모든 예시의 <code>&lt;placeholder&gt;</code>는 실제 값으로 교체할 자리이며 실측 결과가 아니다.

## A. 원칙·적용 범위·용어

### A.1. 적용과 우선순위

1. 사용자가 명시한 프로젝트별 요구조건 > 데이터·분야별 필수 지침 > 이 공통표준 순으로 적용한다. 다만 상위 법적·윤리적 의무와 접근 권한을 우회하는 근거로 삼지 않는다.
2. 충돌이 생기면 적용한 요구, 충돌 내용, 선택 이유, 결과에 미치는 영향과 대체 경로를 해당 노트북의 결정 기록에 남긴다. 분석 전이라면 작업 보고에 남긴다. 기존 산출물을 사용자 지시 없이 삭제·덮어쓰거나 저장소를 일괄 재편하지 않는다.
3. 분야별 변수, 가설 수, 통계모형, 유의수준, 보정법, 표본기간, 성능지표는 공통값으로 고정하지 않는다. 프로젝트 설계와 데이터 특성에 맞게 정하고 근거를 남긴다.
4. 실행한 결과만 관찰 사실로 적는다. 관찰, 가능한 해석, 현재 근거로 확정할 수 없는 주장을 구분한다. 비유의 결과를 효과 없음으로 단정하거나, 관찰적 연관을 설계 근거 없이 인과효과로 확대하지 않는다.
5. 원자료와 기존 결과를 보존하고, 하나의 계산 결과에서 노트북 출력·표 원본·그림 원본·HTML을 파생한다. 서로 다른 파일의 유리한 숫자를 골라 결합하지 않는다.

### A.2. 산출물의 역할과 공통 근거

| 산출물 | 책임 | 포함할 내용 | 대신할 수 없는 것 |
|---|---|---|---|
| STEP notebook | 단계별 실행 및 의사결정 추적 | 입력, 처리·계산, 실제 출력, 결정 이유, 관찰·해석·한계, 검증 상태 | 코드 없는 결과 요약만으로 실행 기록을 대체하지 않음 |
| FINAL notebook | 전체 연구를 논문 본문 수준으로 통합 | 연구질문별 핵심 방법·표·그림, 종합 해석, 재현 가능한 연결, Appendix | STEP 셀을 순서대로 복사한 모음집이 아님 |
| results table | 재사용 가능한 기계 판독 수치 원본 | 충분한 정밀도의 값, 식별키, 단위·표본·사양의 의미 | HTML의 반올림된 화면 표가 원본을 대체하지 않음 |
| results figure | 재사용 가능한 시각 원본 | 논문에 쓸 크기·해상도의 그림과 설명 | 노트북 화면 스크린샷으로 대체하지 않음 |
| HTML summary | 독립적으로 읽는 단계별 연구 보고서 | 핵심 결론, 맥락·방법, 결과 근거, 해석 범위·한계·다음 단계 | 기술적 실행·결정 기록 전체를 맡기지 않음 |

기본 근거 흐름은 **입력 데이터 → STEP 계산·검증 → tables/·figures/ → FINAL 및 HTML**이다. FINAL이 직접 재계산하면 STEP과 동일한 정의·사양을 적용하고 저장 결과와 대조한다. 공통 계산 함수나 승인된 결과 파일을 재사용할 수 있으나, 어느 입력·버전에서 비롯되었는지 설명해야 한다.

### A.3. 레퍼런스 확인과 추상화 범위

이 표준 작성 시 다음 세 파일을 실제로 읽었다. 경로는 기준 저장소에 대한 상대경로이며, 다른 프로젝트가 이 파일을 보유해야 한다는 뜻은 아니다.

| 실제 확인 파일 | 관찰한 구조 | 추상화한 규칙 |
|---|---|---|
| <code>notebooks/06_yield_curve_exposure.ipynb</code> | Markdown 64셀·Code 57셀. 첫 셀의 질문·입출력·구성, 다음 셀의 전체 흐름, PART/단계, Decision Box, 저장과 display 병행, 탐색 PART와 부록 | C의 실행·결정 추적 구조 |
| <code>notebooks/FINAL_paper_analysis.ipynb</code> | Markdown 87셀·Code 102셀. 제목·목적·단위 원칙·질문표, 기준 분석에서 질문별 분석으로 연결, 종합 해석의 세 층위, Appendix | D의 연구질문 중심 통합 구조 |
| <code>results/H1_yield_curve/06_summary_final.html</code> | HTML 소스에서 인라인 CSS·JS, hero·카드·좌측 sticky TOC, 반응형 규칙, 15개 section·26개 표·11개 이미지 확인. 이미지 11개 모두 data URI | F의 독립형 구조와 시각적 정보 계층 |

셀·섹션·표·그림 수와 특정 분야의 변수·계수·판정 결과는 참고 정보이며 분량이나 분석내용의 필수값이 아니다. 원본에 남아 있는 <code>summary.md</code> 저장·출처 안내는 이 표준에 채택하지 않는다. 새 단계 요약은 HTML만 사용한다. 기존 파일은 그대로 보존한다.

확인은 노트북 JSON·셀·저장 출력과 HTML 소스의 구조를 읽은 범위다. 원본 분석을 재실행하거나 브라우저 화면의 픽셀 단위 일치를 검증했다는 뜻이 아니다. 향후 정확한 시각적 대조가 필요하면 원본 HTML과 생성 HTML을 같은 열람 조건에서 비교해야 한다. 원본의 개별 분석 주장 자체를 공통 방법론으로 승인하지 않는다.

## B. 프로젝트 폴더·명명·경로 규칙

### B.1. 기존 구조 우선, 새 프로젝트의 권장 구조

작업 전에 저장소 지침, 문서·코드북·기획안, 경로 설정과 기존 산출물 구조를 확인한다. 기존 프로젝트에서는 그 관행과 경로를 유지한다. <code>docs/</code>에는 코드북·기획안·연구 문서·공통규칙이 함께 있을 수 있으며 <code>reports/</code>를 새로 강제하지 않는다.

다음은 **새 프로젝트에 적용하는 권장 구조의 설명 예시**다. 미래 단계의 폴더까지 실제로 미리 만들라는 뜻이 아니다.

~~~text
project/
├── docs/
├── data/
│   ├── raw/                         # 원본 불변
│   └── processed/                   # 전처리·가공 데이터
├── notebooks/
│   ├── 01_<stage>.ipynb
│   ├── 02_<stage>.ipynb
│   └── FINAL_<study>.ipynb
└── results/
    ├── <stage_id>/
    │   ├── tables/
    │   ├── figures/
    │   └── summary/
    │       └── <stage_id>_summary_final.html
    └── <next_stage_id>/              # 해당 단계를 실제 수행할 때 생성
~~~

- <code>data/raw/</code>는 불변 입력이다. 처리 결과는 기존 프로젝트의 가공 데이터 경로에 저장한다. 자료 접근·보관·Git 추적 정책은 해당 저장소와 데이터 규정을 따른다.
- 단계의 실행 범위가 확정되고 산출물을 만들 때 필요한 디렉터리만 생성한다. 분석하지 않은 가설·단계의 결과 폴더를 빈 채로 선생성하지 않는다.
- <code>tables/</code>와 <code>figures/</code>는 후속 분석·논문에 쓸 원본이다. HTML에 삽입한 뒤에도 보존한다.
- 새 단계의 최종 요약은 <code>summary/&lt;stage_id&gt;_summary_final.html</code> 하나로 작성하고 <code>summary.md</code>를 생성하지 않는다. 기술적 설명·결정 기록은 notebook Markdown에 둔다.
- 기존 프로젝트의 단계 루트 HTML 등 다른 배치가 있으면 그 경로를 사용하고 노트북에 예외를 기록한다. 새 표준을 이유로 기존 HTML·Markdown을 이동·삭제하지 않는다.

### B.2. 이름·경로·재실행

영문 스네이크케이스와 일관된 단계 번호를 권장하되, 기존 저장소의 대소문자·접두어 관행을 우선한다. 같은 단계는 노트북, 표·그림, HTML에서 같은 <code>stage_id</code>로 연결한다. 파일명은 내용을 설명해야 하며 <code>final_final2</code>처럼 최신 여부가 불명확한 이름을 피한다.

- 허용 예시: [예시] <code>02_quality_review.ipynb</code>, <code>missingness_by_group.csv</code>, <code>01_distribution_by_group.png</code>.
- 금지/주의 예시: <code>table1.csv</code>만으로 용도를 알 수 없는 명명, 동일 단계의 식별자를 여러 이름으로 혼용, 개인 PC의 절대 경로를 계산 코드에 고정.
- 프로젝트 루트와 <code>pathlib</code> 또는 기존 config를 사용한다. 실행 위치가 저장소 루트인지 <code>notebooks/</code>인지 검증하고, 입력이 없으면 기대 경로와 해결 방법을 명확히 알린다. 파일을 다른 위치로 옮겨야만 실행되는 코드를 쓰지 않는다.
- 같은 데이터의 사본을 노트북별로 만들지 않는다. 정제·집계·버전 분리가 필요하면 변환 목적, 입력 버전과 저장 경로를 기록한다.
- 기존 결과와 이름이 충돌하면 덮어쓰지 않는다. 사용자 지시 또는 승인된 갱신 정책이 있는지 확인하고, 없으면 이유가 드러나는 대체 경로·버전을 사용해 연결 관계를 기록한다.

## C. STEP 노트북 작성 규칙

### C.1. 시작 셀과 구조

첫 셀은 Markdown으로 작성한다. 다음은 **첫 셀의 뼈대 예시**이며 경로·항목을 실제 단계에 맞게 교체한다. 데이터·표·그림 목록에서 계획과 실제 생성 상태를 구별한다. 산출물이 필요 없는 유형은 <code>해당 없음 — &lt;이유&gt;</code>로 적는다.

~~~markdown
# STEP<번호>. <단계명>

## 분석 질문
<이 단계가 답할 질문 또는 데이터 처리 목적>
- 관련 가설: <있는 경우만; 없으면 생략>
- 선행 단계: <노트북/산출물과 연결 이유 또는 독립 단계>

## 입력
| 구분 | 프로젝트 상대경로 | 버전·단위·용도 |
|---|---|---|
| <입력명> | <data/...> | <출처/기준> |

## 출력
| 유형 | 계획 경로·파일명 | 내용 | 상태 |
|---|---|---|---|
| 데이터 | <data/processed/...> | <가공 내용 또는 해당 없음 사유> | <계획/생성/검증> |
| 표 | <results/<stage_id>/tables/...csv> | <표 목록> | <상태> |
| 그림 | <results/<stage_id>/figures/...png> | <그림 목록> | <상태> |

## 구성
<주요 PART와 연결>

## 수행 범위
<이번 단계의 포함·제외 범위와 확정/탐색 분석 구분>
~~~

두 번째 Markdown 셀은 <code>## 전체 수행 흐름</code>으로 시작해 입력 확인 → 처리/방법 → 핵심 결과 → 진단/민감도(해당 시) → 저장/요약/검증 순서를 안내한다. 이후 큰 묶음은 <code># PART A. &lt;이름&gt;</code>, 하위 작업은 <code>## 1단계. &lt;이름&gt;</code>처럼 계층을 일관되게 사용한다. 작은 단계는 불필요하게 여러 PART로 나누지 않는다.

노트북에는 HTML 요약을 만드는 코드를 두지 않는다. HTML 요약이 필요하면 노트북 밖에서 별도로 만들고, 기존 HTML 파일은 사용자 지시 없이 다시 생성하지 않는다.

#### Markdown 작성 문체

노트북의 Markdown 셀과 코드가 출력하는 Markdown(관찰·해석·한계)은 같은 문체를 쓴다.

- 직관적으로 이해할 수 있게 핵심만 짧게 쓴다.
- `-` 목록으로 나열하고 항목 하나에 사실 하나만 담는다.
- 명사형 또는 `~음`·`~함` 종결로 쓴다. `~다`, `~합니다`, `~습니다` 종결은 쓰지 않는다.
- 긴 문단, 같은 내용의 반복, 불필요한 수식어를 쓰지 않는다.
- 예: `- A 13/14 동일`, `- 미해결은 분모에서 제외`, `- 상한 1로 절단됨`

### C.2. 분석 단위의 실행·해석 순서

핵심 분석 단위마다 다음 흐름을 갖춘다. 단위는 하나의 질문이나 결과 묶음이며 모든 코드 셀마다 같은 장문을 반복할 필요는 없다.

1. **목적:** 왜 확인하는지, 무엇을 만들고 어떤 판단에 쓸지 짧게 설명한다.
2. **계산:** 입력·표본·변수 정의·설정이 보이는 실제 코드를 실행한다.
3. **출력:** 표는 <code>display()</code> 등으로 실제 결과를, 그림은 실제 생성된 시각화를 출력한다.
4. **관찰:** 값·방향·패턴·불확실성 등 출력이 직접 보여주는 것을 적는다.
5. **해석과 한계:** 연구질문에 대한 의미, 적용 범위와 후속 검토를 적는다.

표 저장과 display, 그림 저장과 노트북 표시에는 같은 결과 객체를 사용한다. 예컨대 원본 수치를 저장한 뒤 화면만 반올림할 수 있다. 목적에 대응하지 않는 장식용 표·그림을 늘리지 않는다.

실행되지 않은 셀, 이전 실행의 잔존 출력, 추정해서 적은 수치를 근거로 결론을 쓰지 않는다. 임시 탐색은 별도 PART·Appendix 및 <code>exploratory_</code> 같은 구분 가능한 이름으로 표시한다. 탐색에서 발견한 결과를 사전 계획 결과로 바꾸어 서술하지 않는다. 레퍼런스와 단계·셀 개수를 맞추지 않는다.

### C.3. Decision Box

결론·재현성에 영향을 주는 선택에만 <code>### Decision Box N — &lt;결정 제목&gt;</code>을 사용한다. 대상에는 표본 선정·제외, 변수 정의·측정, 결측·이상값, 가중, 병합 기준, 모형·검정, 튜닝, 다중검정 범위와 보정 등이 포함된다. 단순한 import·색상 변경·출력 순서에 박스를 남발하지 않는다.

각 박스에는 다음 필드를 남긴다.

- **문제:** 무엇을 결정해야 하며 어떤 대안이 있었는가.
- **선택:** 채택한 정의·값·사양과 config 또는 코드 위치.
- **근거:** 데이터 특성·설계·진단·문헌 등 검증 가능한 근거. 결과를 보고 선택했다면 그 사실도 명시.
- **결론에 미친 영향/한계:** 표본·추정량·비교 가능성·판정에 미친 영향. 미검증이면 미검증으로 표시.
- **후속 검증:** 필요한 민감도·진단, 수행 여부와 결과 위치 또는 미수행 이유.

허용 예시: [예시] 결측 관측의 제외가 표본 구성에 미치는 영향을 표로 확인하고 제외 기준을 기록. 금지 예시: 유의한 결과가 나오는 설정만 고른 뒤 선택 과정을 숨김.

### C.4. 완료 확인 기록 위치

노트북에 <code># 최종 완료 확인</code> 섹션을 두지 않는다. 생성 파일 목록, 실행 상태, 검증 결과, 미해결점, G의 인수조건 판정은 작업 보고나 Pull Request 설명에 남긴다. 시작 셀의 산출물 목록은 실제 상태로 갱신한다.

파일이 없거나 재실행에 실패했다면 “완료”로 보고하지 않는다. 원인, 실패 셀·입력, 재현 명령 또는 실행 절차, 다음 조치를 작업 보고에 남긴다.

## D. FINAL 통합 노트북 작성 규칙

### D.1. 통합의 기준

STEP을 기계적으로 이어 붙이지 않고 연구질문과 논문 스토리라인을 기준으로 재구성한다. 기준 분석(Baseline)이 필요한 설계는 그 결과부터 시작하고, 그렇지 않은 프로젝트는 자료 개요·품질 점검 등 논리적 출발점을 사용한다. 가설 없는 EDA에도 가설 번호나 채택·기각을 강요하지 않는다.

첫 화면에 제목·전체 목적·질문별 요약표·논리적 흐름·추정치/지표의 해석 단위·판정 원칙을 둔다. 방법이나 수식, 유의성 판정은 해당 연구에 필요한 경우만 명시한다.

다음은 **FINAL의 Markdown 셀 뼈대 예시**다. 제목 단위별로 셀을 나누고 관련 실행 코드·실제 출력을 사이에 배치한다.

~~~markdown
# <연구 제목>
<전체 연구 목적과 분석 범위>

## 해석 단위와 판정 원칙
<추정치/지표의 단위·변환·방향; 검정·가중·불확실성 원칙 또는 해당 없음>

## 연구질문별 요약
| 질문 | 역할·방법 | 근거 STEP/파일 | 핵심 결과·해석 범위 |
|---|---|---|---|
| <질문> | <방법> | <상대경로> | <실행 후 작성; 미실행이면 미확인> |

## 논리적 분석 흐름
<자료/설계 → 기준 분석(해당 시) → 질문별 핵심 분석 → 종합>

# 1. <기준 분석 또는 자료·설계>
## 연구질문과 방법
<설계 근거와 핵심 식/알고리즘>
## 논문용 표·그림
<실제 실행 출력과 파일 대응>
## 결과와 해석 범위
<관찰 → 해석 → 한계>

# 2. <핵심 연구질문>
<방법 → 선별한 표·그림 → 핵심 결과 → 해석 범위>

# 종합 결과와 해석 범위
## 데이터가 직접 보여주는 것
<검증된 결과>
## 가능한 해석
<근거와 조건>
## 이 연구만으로 확정할 수 없는 것
<식별·측정·표본 등의 한계>

# Appendix
## A. 추가 기술통계·보조 분석
## B. 민감도·강건성·상세 진단
## C. STEP과의 차이·연결·재현성 확인
<해당되는 항목만 작성>
~~~

본문에는 핵심 방법/검정식, 논문에 필요한 표·그림과 해석을 선별한다. 중간 시행착오, 보조표, 민감도 세부 사양과 상세 진단은 Appendix로 보낸다. 다만 결론을 바꾸는 민감도나 핵심 한계는 본문에도 요약해 숨기지 않는다.

### D.2. 정의 일관성과 실행

- STEP과 변수 정의·변환 단위·표본·가중·결측 처리·모형·튜닝·검정·보정 범위를 대조한다. 지표가 달라졌다면 직접 비교 가능한 것처럼 서술하지 않는다.
- 불일치 시 수정시각만으로 최신본을 정하지 않는다. 입력 버전, 실행 상태, 코드/설정, 승인 기록과 결과 파일을 확인해 어느 쪽이 유효한지 근거를 남긴다.
- 재구성·표현 정리를 이유로 사용자가 승인하지 않은 계산방식 변경을 하지 않는다. 계산 변경이 필요하면 차이·영향을 기록하고 승인 전에는 기존 결론을 대체하지 않는다.
- 가능하면 커널을 초기화해 위에서 아래로 독립 실행한다. 승인된 STEP 결과 파일을 읽는 설계도 허용하지만 선행 실행, 필요한 입력·버전·생성 절차를 명시한다. 이전 커널의 변수나 개인 PC 전용 파일에 의존하면 재현 완료가 아니다.
- 원본 정의를 유지한 재계산 결과를 공통 결과 파일과 대조하고 허용오차·차이 원인을 기록한다. FINAL 실행이 STEP 결과를 묵시적으로 덮어쓰지 않도록 승인된 출력 경로를 사용한다.

## E. Table/Figure 산출물 규칙

### E.1. 결과표

기본 수치 원본은 <code>tables/</code>의 CSV다. 자료형·크기·사용 목적에 따라 XLSX/Parquet을 추가할 수 있다. 원 수치를 보존하고 표시용 반올림은 별도 단계에서 수행한다. 인코딩·구분자·결측 표기·날짜 형식을 일관되게 정한다.

각 표는 설명 가능한 파일명, 안정된 행 식별키와 명확한 컬럼명을 갖춘다. 단위·표본수·기간·가중 여부·검정 사양·누락값의 의미는 컬럼 또는 노트북의 표 정의와 HTML 주석에서 확인 가능해야 한다. 모든 행에서 일정한 메타정보를 CSV에 억지로 반복할 필요는 없으나 파일명/표 ID로 설명과 연결해야 한다.

추론표에는 해당되는 추정치·불확실성·표본수·검정통계량·원 p-value·보정값과 보정 범위 등을 보존한다. EDA·전처리 표에는 이를 강제하지 않는다. 결측, 계산 불가, 억제된 값, 실제 0을 구별한다. 열 이름만으로 단위가 불명확하면 정의를 추가한다.

허용 예시: [예시] <code>group_id, metric_name, estimate, unit, n</code>과 연결된 표 주석. 금지 예시: 원본 CSV에서 수작업으로 값을 바꾸거나, 표본수·p-value를 추정해서 채움.

### E.2. 결과그림

- <code>figures/</code>에 논문에서 재사용 가능한 크기와 해상도로 저장한다. 권장 출발점은 최종 사용 크기에서 고해상도 PNG(예: 300 dpi)이며 선·문자 중심 그림은 필요시 SVG/PDF를 추가한다. 게재처 사양과 가독성을 우선하고 DPI 숫자만으로 품질을 판정하지 않는다.
- 제목 또는 캡션에서 대상·기간·그룹·분석 질문을 파악할 수 있게 한다. 축·단위·범례·표본/가중 기준을 표시한다. 불확실성을 추정하는 분석은 신뢰구간·오차범위 등 적절한 표현과 그 정의를 제공한다. 분포·결측도 같은 기술 그림에 불필요한 신뢰구간을 붙이지 않는다.
- 패널·범례·작은 글씨·잘린 축을 최종 사용 크기에서 확인한다. 축 절단·로그 변환·색 범위·비교 기준이 판단에 영향을 주면 명시한다.
- 그림 ID/파일명으로 입력 표 또는 계산 결과와 연결한다. 노트북 화면이나 원자료 표의 스크린샷, 숫자의 수동 전사를 원본 대신 사용하지 않는다.

### E.3. 표시 정합성과 민감 데이터

CSV 원 수치 → 표시 형식/반올림 → HTML 표 셀의 대응이 검증 가능해야 한다. 단위 변환·비율 계산은 생성 코드에서 수행하고 분모와 수식을 밝힌다. 매우 작은 p-value를 화면에서 임의로 0으로 만들지 말고 “표시 기준값 미만” 등 정의된 형식을 사용하며 원값을 보존한다. HTML 그림은 <code>figures/</code>의 최종 파일과 대응해야 한다.

개인·임상 등 민감 자료는 접근·공유 범위와 해당 분야의 기준에 따라 소수 셀, 행 단위 식별정보, 간접 식별과 재식별 위험의 표시를 통제한다. 억제한 값은 0이나 결측과 구분하고 필요한 경우 역산 가능성도 검토한다. 범용 소수 셀 기준값을 임의로 정하지 않는다. HTML에 원자료·비밀 경로·인증정보를 내장하지 않는다.

## F. 각 STEP HTML 보고서 작성 규칙

### F.1. 독립적으로 읽는 정보구조

<code>06_summary_final.html</code>에서 확인한 **결론 우선·근거 추적·카드와 본문의 계층·좌측 TOC·독립형 파일**을 기본 디자인 언어로 사용한다. 특정 분야의 가설 카드나 원본의 섹션 개수를 복제하지 않는다.

다음은 실행 코드가 아닌 정보구조 예시다.

~~~text
hero
  단계/주제명 + 한 줄 핵심 결론 + 한 문단 요약 + 메타정보
선택: 실제 근거가 있는 KPI / 가설 또는 연구질문 카드
shell
  nav.toc: 각 본문 section의 고유 id로 이동
  main
    ① 연구 맥락·목적
    ② 핵심 결론·핵심 결과
    ③ 데이터·방법
    ④ 주요 분석 결과: 표·그림·관찰·해석·한계
    ⑤ 견고성·민감도 또는 진단 [해당 시]
    ⑥ 한계·주의
    ⑦ 결론·다음 단계
    선택: 부록·용어
footer
  근거 노트북 + 결과 원본의 상대경로/표·그림 ID + 버전·검증 상태
~~~

본문의 ①→② 구조를 사용하더라도 hero의 한 줄 결론과 핵심 결과는 상세 방법보다 먼저 노출한다. 필요하면 핵심 결론을 첫 본문 섹션으로 옮긴다. 섹션·카드·표·그림 수는 내용에 맞게 조정하며 작은 보고서에서는 중복 섹션을 합칠 수 있다.

메타정보는 실제 확인된 분석 대상·범위/기간·표본 기준·실행 버전/일자·완료 상태 중 필요한 항목을 포함한다. 가설이 없는 EDA나 전처리에는 연구질문·품질 점검 목적을 표시하며 가설 채택/기각 UI, 유의성 또는 인과성 주장을 억지로 넣지 않는다. 실제 데이터가 없는 KPI를 채우지 않는다.

### F.2. 시각 구성 요소와 토큰

| 요소/클래스 예 | 기능과 적용 기준 |
|---|---|
| <code>hero</code> | 단계명·요약·핵심 결론·메타정보를 가장 먼저 전달 |
| <code>nav.toc</code> | 넓은 화면의 좌측 고정형 목차(sticky 권장), 본문 앵커 이동과 현재 위치 표시 |
| <code>result-box</code> | 가장 중요한 결과와 조건을 짧게 강조 |
| <code>card</code> | 방법·질문·결과의 의미 있는 묶음 |
| <code>dark</code> | 종합 해석이나 최종 메시지의 시각적 구분 |
| <code>warning</code> / <code>good</code> | 주의점 / 기준 충족 등 상태 표현. 텍스트 설명을 반드시 병기 |
| <code>tablewrap</code> | 좁은 화면에서 표 자체만 가로 스크롤 |
| <code>figure</code> / <code>figcap</code> | 그림과 해당 캡션의 결합 |
| <code>cap</code> | 표 주석·단위·출처·판정 기준의 설명 |

권장 토큰 예시는 네이비 <code>#0f172a</code>, 블루 <code>#2563eb</code>, 배경 <code>#f8fafc</code>, 경계 <code>#e2e8f0</code>다. 원본처럼 hero·섹션 제목·카드·표 머리글의 계층을 구분하고 넉넉한 여백, 본문 폭과 줄간격, 일관된 숫자 정렬을 사용한다. 색·글꼴·폭은 프로젝트 맥락에 맞게 조정할 수 있다. 클래스 이름이나 장식 효과 자체보다 정보 계층·대비·가독성을 유지하는 것이 필수다.

<code>good</code>가 가설의 진실을 보증하는 것처럼 보이지 않게 한다. 비유의·조건부·미확인 상태를 색 하나로 뭉뚱그리지 말고 문구로 구별한다. 장식이나 KPI 카드가 본문의 핵심 조건을 가리지 않게 한다.

### F.3. 근거에서 설명까지 연결

1. 모든 결과 주장에 실제 결과 파일의 근거를 연결한다. 정성적 배경·방법 설명은 확인한 문헌/설계 문서를 출처로 구분한다. 숫자·p-value·단위·표본수·가중 여부를 임의로 작성하지 않는다.
2. HTML 표는 <code>tables/</code> 원본을 읽어 만들고 그림은 <code>figures/</code> 최종 파일에서 가져온다. 본문·캡션/주석에 표·그림 이름/ID와 프로젝트 상대 소스 경로를 기록한다. 경로는 출처 정보이며 오프라인 열람에 필요한 외부 파일 참조가 아니다.
3. 각 주요 결과 묶음은 **수치/그림/근거 → 관찰 → 해석 → 한계**로 설명한다. hero의 요약 결론도 이 근거 묶음으로 되돌아갈 수 있어야 한다.
4. 표에는 제목·단위·표본수·가중 여부·주요 사양·반올림·결측 표기를 설명한다. 그림에는 캡션·대체텍스트와 주요 조건을 둔다. 해당 없는 항목은 억지로 생성하지 않는다.
5. 조건부·비유의·불확실한 결과와 진단 실패를 분명히 표시한다. 결과가 민감도에 따라 달라지면 주 사양 결과와 대안 결과를 함께 설명한다. 검정으로 확인하지 않은 차이를 “유의한 차이”라고 쓰지 않는다.

허용 예시: [예시] 표 <code>&lt;table_id&gt;</code>의 관찰과 조건을 요약하고, 추정 불확실성 때문에 확정할 수 없는 부분을 명시. 금지 예시: 파일에 없는 수치를 KPI로 생성, 탐색적 결과를 확증으로 표시, 주석 없이 서로 다른 표본의 값을 한 표에서 비교.

### F.4. 오프라인 단일 파일과 접근성

- 배포용은 CSS·필요한 가벼운 JS·그림을 포함한 단일 HTML을 원칙으로 한다. PNG 등은 data URI로, SVG는 인라인 등 자체 포함 방식으로 넣는다. 외부 CDN·웹폰트·스크립트·스타일시트·절대 로컬 이미지 경로에 의존하지 않는다.
- 외부 문헌 링크는 허용하지만 핵심 내용·이미지·탐색이 네트워크 없이는 작동하지 않는 구조는 허용하지 않는다. 원본 표·그림은 별도 보존하며 HTML이 이를 대체하지 않는다.
- <code>lang</code>, UTF-8, viewport, 문서 제목과 의미 있는 제목 계층을 설정한다. 각 TOC 링크는 중복 없는 실제 section ID를 가리켜야 한다. JS가 없어도 기본 앵커 이동과 핵심 내용 열람은 가능해야 한다.
- 넓은 화면에서는 목차가 읽는 위치를 따라가고, 좁은 화면에서는 상단 목차 등으로 바꿔 본문을 가리지 않게 한다. 그림은 비율을 유지해 축소하고 표는 <code>tablewrap</code> 안에서 스크롤한다. 본문 전체가 옆으로 밀리지 않게 한다.
- 키보드로 목차·표 스크롤에 접근할 수 있게 하고 포커스가 보이게 한다. 표의 제목·열/행 머리글, 그림의 의미 있는 대체텍스트를 제공한다. 판정은 색과 함께 기호·문구로 표시한다.
- 인쇄 규칙에서 고정 목차·불필요한 UI를 정리하고, 어두운 카드의 글자가 사라지지 않게 한다. 가로 스크롤 표의 열이 인쇄에서 잘리지 않도록 축소·줄바꿈·가로 페이지 등 적절한 방법을 적용한다. 캡션·주석과 그림의 분리를 줄이고 인쇄 미리보기로 확인한다.
- 기능·그림 임베딩과 접근성은 실제 생성본에서 검증한다. 원본에 존재하지 않거나 확인하지 않은 품질을 원본의 특성으로 단정하지 않는다.

<code>summary.md</code>는 생성하지 않는다. notebook은 기술적 실행·의사결정 기록, HTML은 공유용 스토리라인을 맡고 <code>tables/</code>·<code>figures/</code>를 공통 근거로 사용한다.

## G. 실행·검증·완료 기준

### G.1. 검증 방식과 기록

노트북 JSON 유효성, 커널·언어·환경 설정, 의존성·입력 데이터 버전·난수 설정(해당 시)을 점검한다. 가능하면 커널 초기화 후 상단부터 순서대로 실행하고 실제 값과 출력을 저장한다. 숨은 상태, 오류 출력, 오래된 출력과 현재 코드의 불일치를 확인한다. 실행 번호가 있다는 이유만으로 재현된 것으로 보지 않는다.

실행이 데이터를 갱신하거나 기존 결과를 덮어쓸 수 있으면 먼저 승인된 경로·갱신 정책을 확인한다. 검증용 실행도 기존 산출물을 임의로 바꾸는 예외가 되지 않는다. STEP 간 필요한 실행 순서를 명시하고, FINAL이 공통 결과와 같은 정의·값을 재현하는지 확인한다.

수치 대조는 표 ID·행 키·컬럼·사양을 맞춘 뒤 수행한다. CSV의 헤더·자료형·주요 값·단위·행 수를 확인하고, 표시 반올림이나 확률적 계산의 허용오차는 사전에 근거를 정한다. 다른 표본·설정의 차이를 허용오차로 덮지 않는다.

HTML은 소스 검사에 더해 실제 브라우저에서 네트워크 없이 열어 모든 이미지의 디코딩·로딩, TOC 앵커, CSS·JS, 표·그림 누락과 캡션·출처를 확인한다. 넓은 화면·좁은 화면·인쇄 미리보기를 확인한다. 수행하지 못한 검증을 통과로 표시하지 않는다.

### G.2. 단계별 인수조건 및 실패 시 조치

각 STEP의 작업 보고와 FINAL의 재현성 확인에 아래 **11개 항목**을 사용한다. 판정은 <code>통과 / 실패 / 미검증 / 해당 없음(사유)</code>로 기록한다. 근거 경로·실행 절차는 작업 보고나 Pull Request 설명에 남기며 별도 체크리스트 파일을 필수로 만들지 않는다.

- [ ] **1. 범위·입출력 확정:** 질문·수행 범위·선행 단계·실제 파일 목록과 경로가 일치한다. 실패 시 누락·중복·충돌을 정리하고 미실행 산출물을 계획 상태로 되돌린다.
- [ ] **2. 노트북 형식·환경:** JSON이 유효하고 커널·의존성·입력 버전·해당 난수 설정을 확인할 수 있다. 실패 시 형식/환경을 바로잡고 실제 재검증 전 완료를 보류한다.
- [ ] **3. 실행·출력 보존:** 초기 커널에서 순차 실행이 성공하고 오류 출력 없이 최신 실행값이 저장되어 있다. 실패/불가 시 셀·원인·재현 명령/실행 절차와 마지막 성공 범위를 남겨 미완료로 표시한다.
- [ ] **4. 정의·결정 일관성:** 중요 결정이 기록되고 STEP/FINAL의 표본·단위·사양·보정이 일치하거나 차이 근거가 있다. 실패 시 유효한 원본과 승인 이력을 확인하고 임의 계산 변경을 중단한다.
- [ ] **5. 결과표 검증:** CSV가 존재하고 열림·헤더·자료형·행 수·단위·표본·가중·누락 표기·주요 값이 기대와 맞는다. 실패 시 생성 과정을 수정하고 수동으로 값을 메우지 않는다.
- [ ] **6. 결과그림 검증:** 그림이 존재하고 정상 열림·크기·해상도·축·범례·불확실성·캡션 대응을 확인했다. 실패 시 원본 계산에서 다시 생성하고 검증 전 배포하지 않는다.
- [ ] **7. 매체 간 정합성:** notebook/디스크, CSV/HTML의 값·반올림·단위, figures/HTML의 그림과 핵심 주장 근거가 대응한다. 실패 시 입력·사양·버전을 추적해 차이를 해결한 뒤 파생물을 갱신한다.
- [ ] **8. HTML 독립성·탐색:** 오프라인 단일 파일에서 모든 img와 인라인 SVG, TOC 앵커, CSS·필요 JS와 핵심 내용이 정상 동작한다. 실패 시 누락 자원·깨진 ID·외부 의존을 고친 후 다시 열어 확인한다.
- [ ] **9. 화면·접근성·인쇄:** 넓은/좁은 화면의 목차·표 스크롤·그림, 대체텍스트·키보드·색 이외의 표시와 인쇄 가독성을 확인했다. 실패 시 레이아웃·표시를 수정하고 해당 조건에서 재검증한다.
- [ ] **10. 해석·공유 적합성:** 관찰/해석/한계와 탐색/확증을 구별하고 미확인 숫자·과도한 주장·민감정보 노출이 없다. 실패 시 주장·표시 범위를 수정하고 해당 분야 기준을 다시 적용한다.
- [ ] **11. 최종 인수 기록:** 실제 산출물·검증 상태·미해결점·후속 단계와 재현 절차가 기록되며 기존 결과 보존을 확인했다. 실패 시 완료 표시를 보류하고 부족한 근거와 다음 조치를 남긴다.

필수 항목에 실패나 미검증이 남으면 전체를 완료로 선언하지 않는다. 부분 완료 범위와 남은 작업을 분리해서 보고한다. 해당 없음은 적용 사유가 실제로 없는 항목에만 사용한다. 예컨대 그림이 필요 없는 단계는 사유를 기록할 수 있지만, 만들어야 할 그림이 누락된 상태는 해당 없음이 아니다.

## H. 도입 방법과 예외 관리

### H.1. 다른 프로젝트에서 참조하는 방법

문서 하나를 저장했다고 Codex의 모든 프로젝트에 자동 적용되지는 않는다. 다음 중 한 방식으로 새 작업에서 읽을 수 있는 경로를 명시한다.

1. **작업 지시문에서 참조:** [예시] “작업 전에 &lt;접근 가능한 표준 문서 경로&gt;/RESEARCH_OUTPUT_STANDARD.md를 읽고 적용하라. 프로젝트 고유 요구와 충돌하면 이유와 적용 방식을 기록하라.”
2. **프로젝트 지침에서 참조:** 사용자가 선택한 프로젝트 지침(예: 기존 <code>AGENTS.md</code>)에 표준의 위치와 적용 우선순위를 명시한다. 프로젝트에 이 문서를 두면 <code>docs/RESEARCH_OUTPUT_STANDARD.md</code>처럼 상대경로로 참조한다.
3. **공유 원본 참조:** 여러 프로젝트가 접근할 수 있는 문서 위치나 버전이 고정된 저장소 링크를 사용하고, 각 프로젝트에서 실제 읽을 수 있는지 확인한다. 링크만 적고 읽은 것으로 간주하지 않는다.

사용자가 해야 할 일은 향후 프로젝트의 작업 지시 또는 지침에 유효한 참조 경로를 지정하고, 필요한 프로젝트별 예외·추가 조건을 전달하는 것이다. 다른 저장소의 지침 편집이나 표준 배치는 해당 프로젝트 작업에서 수행한다. **이 표준 작성 작업에서는 별도 AGENTS.md·템플릿·스크립트·규칙 문서를 생성·수정하지 않는다.**

### H.2. 예외와 유지보수

기존 프로젝트에 일괄 폴더 이동·이름 변경·요약 파일 삭제를 적용하지 않는다. 새 프로젝트에서 권장 구조를 기본으로 삼고, 기존 프로젝트는 다음 내용을 해당 STEP 또는 FINAL의 결정/재현성 기록에 남긴다.

| 예외 기록 필드 | 기록 내용 |
|---|---|
| 대상 규칙과 이유 | 기존 구조, 데이터 규정, 도구 제약 등 구체적 사유 |
| 적용 범위와 대체 경로/방법 | 어떤 단계·파일에 한정하는지와 실제 저장·참조 방법 |
| 결과·재현성 영향 | 비교 가능성·독립 열람·검증에 미치는 영향 |
| 승인 또는 근거·해결 상태 | 사용자 지시/적용 지침, 남은 조치와 완료 여부 |

허용 예시: 기존 단계 루트에 HTML을 유지하면서 notebook에 상대경로를 명시. 금지 예시: 표준 도입을 이유로 과거 결과를 전부 이동하거나 사용자 승인 없이 기존 계산을 바꿈.

예외를 기록해도 근거 없는 결과 작성, 미완료의 완료 표시, 원자료·기존 결과의 임의 삭제는 허용되지 않는다. 표준을 갱신할 때에는 공통적인 산출물 문제를 다루고, 분야별 분석 방법론은 프로젝트의 기획안·코드북·설계 문서에 둔다. 이 문서를 도메인별 방법론 백과사전으로 확대하지 않는다.
